# Resume Fact Check (resume-next 로컬 스킬)

설치된 외부 이력서 스킬들은 미국 시장 기준이고, 일부는 **추정치를 만들어 넣으라고** 권한다
(예: resume-quantifier "If you think it was 60%, say 50%"). 예시 문구도 전부 가상의 숫자다.
이 스킬은 그 위에 얹는 **우선 규칙**이다. 외부 스킬 지침과 충돌하면 이 스킬이 이긴다.

## 1. 우선 규칙 (외부 스킬 override)

1. **숫자는 근거가 있을 때만 쓴다.**
   - 허용: `src/lib/data/portfolio-metrics.ts`에 있는 값, 저장소 코드·문서·커밋에서 확인한 값,
     사용자가 이번 대화에서 직접 알려준 값.
   - 금지: 추정, "보수적으로 깎은" 추정, 범위로 뭉갠 추정, 외부 스킬 예시에서 가져온 숫자.
   - 근거가 없으면 문장에 `[확인 필요: 무엇]`을 남기고 사용자에게 묻는다. 지어 넣지 않는다.
2. **전문용어는 구현 근거가 있을 때만 쓴다.**
   - 용어마다 "이걸 실제로 만든 코드/문서가 어디 있나?"를 확인한다.
   - 면접 꼬리질문 3개(무엇을 썼나 / 왜 그걸 골랐나 / 결과를 어떻게 쟀나)에 답할 수 없으면 뺀다.
   - 예: RAG·임베딩·벡터 검색은 2026-11 기준 사용자 저장소 어디에도 구현이 없다.
     실제로 만들기 전까지 이력서에 쓰지 않는다.
3. **역할 범위는 사용자 확인을 받는다.** "주도·설계·리드"와 "참여·지원"은 다르다. 모르면 묻는다.
4. **타인 프로필을 수집하지 않는다.** resume-tailoring의 Phase 1.3(LinkedIn 프로필 3~5개 WebFetch로
   벤치마킹)은 건너뛰고, 공개된 채용 공고·회사 기술 블로그만 쓴다.
5. **출처 없는 통계를 근거로 들지 않는다.** 예: "이력서 75%가 ATS에서 탈락"은 2012년 업체 마케팅
   문구에서 나온 수치로 검증된 연구가 없다(`docs/resume-optimization-research.md` 참고).
6. **문서 출력 스킬 이름:** resume-tailoring이 말하는 `document-skills:docx` / `document-skills:pdf`는
   이 환경에서 `anthropic-skills:docx` / `anthropic-skills:pdf`다.

## 2. 한국 개발자 이력서 관례

- 맨 위 한 줄로 "어떤 개발자인지" 요약하고, 제목에 자신을 설명하는 키워드를 넣는다.
  요약 문단은 본문을 다 쓴 뒤 마지막에 쓴다.
- 채용 담당자는 한 장을 짧게(약 15초 안팎) 훑는다. 핵심 성과와 공고와 맞는 기술을 위에 둔다.
- 경력기술서는 **프로젝트 단위**로 나눈다. 각 프로젝트는
  **문제 → 내 역할 → 기술 선택 이유 → 성과** 순서로 쓴다.
- 링크("자세한 건 링크 참고")에 기대지 말고 핵심은 본문에 쓴다. 링크는 보조다.
- AI 경험은 "도구를 썼다"가 아니라 **무엇을 판단했고 무엇을 만들었고 결과가 어땠는지**를 쓴다.
- 기술 스택은 지원 공고의 표기와 맞춘다(예: 공고가 "Next.js"면 "넥스트" 대신 "Next.js").

## 3. 확인 절차

1. 문장을 **주장 단위**로 쪼갠다. (한 문장에 주장이 2~3개 섞여 있는 경우가 많다.)
2. 주장마다 근거를 붙인다:
   - `[코드] 경로:줄` / `[커밋] SHA` / `[문서] 경로` / `[사용자 확인] 날짜` / `[근거 없음]`
3. `[근거 없음]`은 삭제하거나, `[확인 필요]`로 표시하고 사용자에게 묻는다.
4. 꼬리질문 테스트(규칙 2)를 통과하지 못한 용어를 뺀다.
5. 상투 문구를 걷어낸다: "results-driven", "proven track record", "열정적인", "다양한 경험",
   "성공적으로 수행", "significantly/dramatically improved"(숫자 없이) 등.
   필요하면 `humanizer` 스킬로 한 번 더 다듬는다.
6. ko/en 두 언어를 함께 고친다. 한쪽만 바뀌면 안 된다.

## 4. 출력 형식

```markdown
| # | 주장 | 근거 | 상태 | 조치 |
|---|------|------|------|------|
| 1 | 크래시율 3.89% → 0.02% | [코드] src/lib/data/portfolio-metrics.ts | ✅ | 유지 |
| 2 | 사용자 55만 명 | [코드] portfolio-metrics.ts `users` | ✅ | 유지 |
| 3 | RAG 파이프라인 구축 | [근거 없음] | ❌ | 삭제 — 구현 없음 |
| 4 | 리뷰 시간 40% 단축 | [근거 없음] | ⚠️ | [확인 필요: 측정값 있는지] 질문 |
```

표 아래에 수정된 최종 문장(ko/en)과 사용자에게 물을 질문 목록을 붙인다.

## 5. resume-next에서 내용이 사는 곳

- 숫자 단일 출처: `src/lib/data/portfolio-metrics.ts`
  (`.cursor/rules/context-anchor.mdc`의 Metrics 규칙과 같다)
- 프로젝트: `src/lib/data/projects/projects.tsx` (ko/en 분기)
- 화면 문구: `src/lib/i18n/dictionaries.ts` (ko/en)
- 외부 링크: `src/lib/data/links.ts`
- 근거 원천: 사용자 저장소(wemake, local_llm=Shorts Factory, ai-web-summarizer 등)의 코드·docs·커밋
